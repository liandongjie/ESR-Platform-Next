# 2026-08-20 隔离 RC 发布与恢复演练

## 边界

本报告来自本机 Docker Desktop 的隔离项目，不是火山引擎生产操作。所有测试容器和卷使用
`esr-release-gate-*`、`esr-platform-next-rc` 或 `esr-restore-drill-*` 命名；未停止、删除或挂载
已有默认 Compose project 的数据库/runtime 卷。

## Migration 发布门

使用 Backend production image 在全新 PostGIS 16-3.4 数据库中执行：

1. `upgrade`：依次执行 `20260820_01`、`20260820_02`、`20260820_03`；
2. `downgrade -- -1`：回到 `20260820_02`；
3. 再次 `upgrade`：恢复 `20260820_03`；
4. 启动 production Gunicorn，`/health/ready` 校验数据库 revision 与仓库 head 一致。

结果：PostGIS 3.4.3、最终 revision `20260820_03`、readiness 200。首次真实执行发现 PowerShell
脚本把 `-1` 传给 Click 时缺少 `--`，修复后发布门通过；finally 只清理唯一隔离 project。

## Redis 短暂不可用

演练前数据库确认 QUEUED/RUNNING 任务数为 0。停止 Redis 后 readiness 返回 503；重新启动后：

- readiness 从 Redis start 起 0.819 秒恢复；复验为 0.406 秒；
- Celery Worker ping 从 Redis start 起 11.204 秒恢复；
- 数据库和 runtime 无变化。

发现：关闭容器会让 Docker DNS 中 `redis` 服务名暂时消失，即使 Web Redis 客户端关闭库级
重试，人工 readiness 的 503 响应仍约需 15.8 秒；Compose 的 5 秒 healthcheck timeout 会直接
把该次探测判失败，不会误报健康。连接拒绝场景已通过 `Retry(NoBackoff(), 0)` 避免 redis-py
默认 3 次指数退避，但 Docker DNS 解析等待仍是已知限制。

## Worker 停止与恢复

1. 确认无活动任务后停止唯一 Worker；
2. 通过认证 API 提交小型三指标任务；
3. 状态端点确认任务保持 `QUEUED`；
4. 启动 Worker 并轮询终态。

结果：task `b04a8c8d-4d91-4f5d-aba1-664026ab9028` 最终 `SUCCEEDED`；恢复墙钟 4.164 秒，
服务端排队 3.789 秒、执行 0.108 秒。任务未丢失，也没有重复发布成果。
